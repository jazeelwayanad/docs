## Admin login

Host: `admin.<ROOT_DOMAIN>` · Route: `/login`

### Purpose and access

Sign into the administrator application using an account email and password.

Entry, public access, and redirect rules are described for this screen below.

### Screen layout

Welcome back appears above the LoginForm with email/password, notices for inactivity/expiry, and Log in. The authentication shell links to registration where shown.

### Fields and displayed information


#### Fields and filters: Login form

| Field / control | Reference | Input | Required marker | Choices / hints / initial values |
| --- | --- | --- | --- | --- |
| Email | `login-email` | email | Yes | you@example.com |
| Password | `login-password` | password | Yes | •••••••• |



### Actions


| Control | Result | Component |
| --- | --- | --- |
| Log in | Submits the associated API change; follow the sequence and failure rules below. | `login-form.tsx` |


#### Linked navigation

| Link | Target in source |
| --- | --- |
| Sign up | `/register` |



### Interaction sequence

Enter email and password → Log in → submit /auth/login → navigate to a safe returnTo/redirect path or the configured destination. The admin root then selects the first managed Mahallu.

### States and rules

The form exposes field/general errors and loading. Safe return paths must begin with one slash. An authenticated login visit redirects rather than showing the form.

The rendered action controls bind loading indicators to pending state. Failed API saves keep their documented error/notification path; a loading indicator alone does not establish persistence.

### Implementation references

Paths below are relative to the application repository. This is source-reviewed behavior, not a recorded browser test.

- `apps/web/src/app/sites/admin/login/page.tsx`
- `apps/web/src/features/auth/login-form.tsx`

Data and access helpers: `apps/web/src/lib/session.ts`, `apps/web/src/lib/server-api.ts`, `apps/web/src/lib/api-client.ts`

## Admin registration

Host: `admin.<ROOT_DOMAIN>` · Route: `/register`

### Purpose and access

Create an administrator identity before managing a Mahallu.

Entry, public access, and redirect rules are described for this screen below.

### Screen layout

Create your account contains full name, email, password, confirmation, and Create account.

### Fields and displayed information


#### Fields and filters: Register form

| Field / control | Reference | Input | Required marker | Choices / hints / initial values |
| --- | --- | --- | --- | --- |
| Full name | `register-name` | text | Yes | Enter your full name |
| Email | `register-email` | email | Yes | you@example.com |
| Register password | `register-password` | password | Yes | Create a password |
| Confirm Password | `confirm-password` | password | Yes | Confirm your password |



### Actions


| Control | Result | Component |
| --- | --- | --- |
| Create account | Submits the associated API change; follow the sequence and failure rules below. | `register-form.tsx` |


#### Linked navigation

| Link | Target in source |
| --- | --- |
| Log in | `/login` |



### Interaction sequence

Complete the fields → Create account → submit /auth/register → navigate to the admin entry point; a user without a managed Mahallu is sent to onboarding.

### States and rules

The form validates missing/invalid values and password confirmation, then shows API errors when registration fails. Creating an account is distinct from creating the tenant.

The rendered action controls bind loading indicators to pending state. Failed API saves keep their documented error/notification path; a loading indicator alone does not establish persistence.

### Implementation references

Paths below are relative to the application repository. This is source-reviewed behavior, not a recorded browser test.

- `apps/web/src/app/sites/admin/register/page.tsx`
- `apps/web/src/features/auth/register-form.tsx`

Data and access helpers: `apps/web/src/lib/session.ts`, `apps/web/src/lib/server-api.ts`, `apps/web/src/lib/api-client.ts`

## Admin entry routing

Host: `admin.<ROOT_DOMAIN>` · Route: `/`

### Purpose and access

Resolve the starting destination for the signed-in administrator.

Entry, public access, and redirect rules are described for this screen below.

### Screen layout

This route renders no dashboard or tenant chooser.

### Fields and displayed information


This screen has no editable fields or filters in its rendered components.


### Actions


Navigation and row interactions are described in the sequence below.


### Interaction sequence

No session → /login. With memberships → /{firstTenantSlug}. Without memberships → /onboarding.

### States and rules

The current implementation always selects the first returned tenant. It does not expose a workspace selection screen for multiple memberships.
