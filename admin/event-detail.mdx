## Event detail

Host: `admin.<ROOT_DOMAIN>` · Route: `/[tenant]/events/[eventId]`

### Purpose and access

Inspect an event’s registrations and associated income/expenditure.

You need an account session and a resolved membership context in the selected Mahallu (including the API’s current platform elevation path). The API independently checks the requested operation’s permissions and feature availability.

### Screen layout

The page shows the event heading, a Registrations table, and Income & expenditure. Registration actions operate on event-specific records.

### Fields and displayed information


Displayed table columns: **Participant**, **Phone**, **Attended**, **Actions**.

#### Fields and filters: Event registrations table

| Field / control | Reference | Input | Required marker | Choices / hints / initial values |
| --- | --- | --- | --- | --- |
| Name | `name` | text | Not marked | Participant name |
| Phone | `phone` | text | Not marked | Phone (optional) |
| Registration.attended | `registration.attended` | checkbox | Not marked | — |



### Actions


| Control | Result | Component |
| --- | --- | --- |
| Register | Submits the associated API change; follow the sequence and failure rules below. | `event-registrations-table.tsx` |
| Remove | Submits the associated API change; follow the sequence and failure rules below. | `event-registrations-table.tsx` |


#### Linked navigation

| Link | Target in source |
| --- | --- |
| ← All events | `/${slug}/events` |



### Interaction sequence

Open an event from Events → enter a participant name and optional phone → Register → the fields reset and the list refreshes. Toggle attendance for a saved participant or confirm removal → refresh. Review linked financial records in the income/expenditure panel.

### States and rules

The event is resolved within the tenant. Missing or unavailable events use notFound. Registration status changes and finance totals are separate concerns.

The rendered action controls bind loading indicators to pending state. Failed API saves keep their documented error/notification path; a loading indicator alone does not establish persistence.

### ഉദ്ദേശ്യവും പ്രവേശനവും

പരിപാടിയുടെ രജിസ്ട്രേഷനുകളും ബന്ധപ്പെട്ട വരവ്/ചെലവും പരിശോധിക്കുക.

Account sessionഉം തിരഞ്ഞെടുത്ത മഹല്ലിൽ resolved membership contextഉം വേണം; APIയിലെ നിലവിലെ platform elevation pathഉം ഇതിൽപ്പെടും. ഓരോ പ്രവർത്തനത്തിന്റെയും permissions/features API പ്രത്യേകം പരിശോധിക്കുന്നു.

### പ്രവർത്തനക്രമം

Eventsൽ നിന്ന് പരിപാടി തുറക്കുക → participant name, ഐച്ഛിക phone നൽകുക → Register → fields reset ചെയ്ത് പട്ടിക പുതുക്കും. Attendance മാറ്റുകയോ സ്ഥിരീകരിച്ച് നീക്കുകയോ ചെയ്യുക → പുതുക്കും. ധനകാര്യ വിഭാഗത്തിൽ ബന്ധപ്പെട്ട രേഖകൾ കാണാം.

### നിലകളും നിയമങ്ങളും

മഹല്ലിനുള്ളിൽ നിന്നാണ് പരിപാടി വായിക്കുന്നത്. ലഭ്യമല്ലെങ്കിൽ notFound ഉപയോഗിക്കുന്നു. രജിസ്ട്രേഷൻ സ്ഥിതിമാറ്റവും ധനകാര്യ കണക്കുകളും വ്യത്യസ്ത കാര്യങ്ങളാണ്.

Rendered action controls pending state അനുസരിച്ച് loading indicator കാണിക്കുന്നു. API save പരാജയപ്പെട്ടാൽ ബന്ധപ്പെട്ട error/notification കാണിക്കും; loading indicator മാത്രം persistence തെളിയിക്കുന്നില്ല.
