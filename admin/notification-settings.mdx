## Notification settings

Host: `admin.<ROOT_DOMAIN>` · Route: `/[tenant]/settings/notifications`

### Purpose and access

Configure service/dues alerts, event reminders, and SMS-provider metadata.

You need an account session and a resolved membership context in the selected Mahallu (including the API’s current platform elevation path). The API independently checks the requested operation’s permissions and feature availability.

### Screen layout

The form has new-service-request and new-dues switches, event reminder days, SMS enablement, provider, and sender ID. Unsaved changes expose a save/reset bar.

### Fields and displayed information


#### Fields and filters: Notification settings form

| Field / control | Reference | Input | Required marker | Choices / hints / initial values |
| --- | --- | --- | --- | --- |
| Notify on new service request | `notifyOnNewServiceRequest` | switch | Not marked | — |
| Notify on new due | `notifyOnNewDue` | switch | Not marked | — |
| Reminder days | `reminder-days` | number | Not marked | min 0; max 30 |
| Sms enabled | `smsEnabled` | switch | Not marked | — |
| Sms provider | `sms-provider` | text | Not marked | e.g. MSG91 |
| Sms sender | `sms-sender` | text | Not marked | e.g. MAHALL |



### Actions


| Control | Result | Component |
| --- | --- | --- |
| Discard | Invokes the associated handler; see the sequence below. | `unsaved-changes-bar.tsx` |
| Save changes | Invokes the associated handler; see the sequence below. | `unsaved-changes-bar.tsx` |



### Interaction sequence

Change settings → review the unsaved-changes bar → save → patch notification settings and refresh; reset discards local edits.

### States and rules

Saving provider metadata is not proof of SMS delivery integration. The route has a denied settings.view state. Numeric reminder values are checked by the form before submission.

The rendered action controls bind loading indicators to pending state. Failed API saves keep their documented error/notification path; a loading indicator alone does not establish persistence.

## Notification settings

Host: `admin.<ROOT_DOMAIN>` · Route: `/[tenant]/settings/notifications`

### ഉദ്ദേശ്യവും പ്രവേശനവും

സേവന/കുടിശ്ശിക അറിയിപ്പുകൾ, പരിപാടി ഓർമ്മപ്പെടുത്തൽ, SMS-provider വിവരങ്ങൾ ക്രമീകരിക്കുക.

Account sessionഉം തിരഞ്ഞെടുത്ത മഹല്ലിൽ resolved membership contextഉം വേണം; APIയിലെ നിലവിലെ platform elevation pathഉം ഇതിൽപ്പെടും. ഓരോ പ്രവർത്തനത്തിന്റെയും permissions/features API പ്രത്യേകം പരിശോധിക്കുന്നു.

### സ്ക്രീൻ ക്രമം

പുതിയ സേവന/കുടിശ്ശിക switches, reminder days, SMS enablement, provider, sender ID എന്നിവയുണ്ട്. സംരക്ഷിക്കാത്ത മാറ്റങ്ങൾക്ക് save/reset bar കാണിക്കും.

### പ്രവർത്തനക്രമം

ക്രമീകരണം മാറ്റുക → unsaved-changes bar പരിശോധിക്കുക → സംരക്ഷിക്കുക → notification settings പുതുക്കും; reset പ്രാദേശിക മാറ്റങ്ങൾ ഉപേക്ഷിക്കും.

### നിലകളും നിയമങ്ങളും

Provider വിവരങ്ങൾ സംരക്ഷിക്കുന്നത് SMS അയക്കൽ integration ഉണ്ടെന്ന തെളിവല്ല. settings.view ഇല്ലെങ്കിൽ പ്രത്യേക നിലയുണ്ട്. Reminder സംഖ്യ form സമർപ്പിക്കുന്നതിന് മുമ്പ് പരിശോധിക്കുന്നു.

Rendered action controls pending state അനുസരിച്ച് loading indicator കാണിക്കുന്നു. API save പരാജയപ്പെട്ടാൽ ബന്ധപ്പെട്ട error/notification കാണിക്കും; loading indicator മാത്രം persistence തെളിയിക്കുന്നില്ല.
