## Services and aid requests

Host: `admin.<ROOT_DOMAIN>` · Route: `/[tenant]/services`

### Purpose and access

Log and review service requests associated with members.

You need an account session and a resolved membership context in the selected Mahallu (including the API’s current platform elevation path). The API independently checks the requested operation’s permissions and feature availability.

### Screen layout

The screen has a Log a request form and a selectable request list with status filtering. Selected request details include Resolution notes and status actions.

### Interaction sequence

Create a request → select it → Start review → Approve or Reject → Mark completed where offered. Rejection/completion can include resolution notes; each action patches the request and refreshes.

### States and rules

The screen checks services access and exposes empty requests separately. Status controls are conditional on the selected request’s status; the presence of a button is not authority to bypass backend permissions.

The rendered action controls bind loading indicators to pending state. Failed API saves keep their documented error/notification path; a loading indicator alone does not establish persistence.

അംഗങ്ങളുമായി ബന്ധപ്പെട്ട സേവന അഭ്യർത്ഥനകൾ രേഖപ്പെടുത്തി പരിശോധിക്കുക.

### പ്രവർത്തനക്രമം

അഭ്യർത്ഥന സൃഷ്ടിക്കുക → തിരഞ്ഞെടുക്കുക → Start review → Approve അല്ലെങ്കിൽ Reject → ലഭ്യമെങ്കിൽ Mark completed. നിരസിക്കലിലും പൂർത്തിയാക്കലിലും കുറിപ്പ് നൽകാം; ഓരോ പ്രവർത്തനവും രേഖ പുതുക്കുന്നു.

### നിലകളും നിയമങ്ങളും

services പ്രവേശനം പരിശോധിക്കുന്നു; അഭ്യർത്ഥനകളില്ലെങ്കിൽ പ്രത്യേക സന്ദേശമുണ്ട്. നിലവിലെ സ്ഥിതി അനുസരിച്ചാണ് ബട്ടണുകൾ വരുന്നത്; ബട്ടൺ കാണുന്നത് backend അനുമതി മറികടക്കാനുള്ള അധികാരമല്ല.

Rendered action controls pending state അനുസരിച്ച് loading indicator കാണിക്കുന്നു. API save പരാജയപ്പെട്ടാൽ ബന്ധപ്പെട്ട error/notification കാണിക്കും; loading indicator മാത്രം persistence തെളിയിക്കുന്നില്ല.
